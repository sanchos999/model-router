# Model Router v1.0 — Руководство администратора (R12-B/R13, финальная редакция)

Дата: 12.09.2026. Коммит: ff75cef (+ R13 release). Продукт: standalone
OI-совместимый LLM-роутер с контрольной плоскостью и Admin UI.

## 1. Архитектура

Model Router — независимый шлюз маршрутизации LLM-запросов. Hermes (или любой
OpenAI-совместимый клиент) отправляет запросы на runtime :4100; router
классифицирует задачу, выбирает модель (canonical) и провайдера (маршрут),
применяет политики (скидка, качество, health, контекст), считает экономику и
прозрачно проксирует запрос с фейловером между маршрутами.

Три уровня изоляции:
- Runtime (:4100, model-router.service) — инференс, не падает при сбое управления.
- Control plane (:4111, model-router-control.service) — Admin API/UI, ревизии,
  discovery, пробы, scheduler. Сбой не влияет на инференс.
- Legacy ~/hermes-router — заморожен, только полный откат (LEGACY_ROLLBACK_ONLY).

## 2. Runtime / Control Plane

Runtime держит registry маршрутов (построен из каталогов провайдеров +
canonical-маппинги), selector (двухуровневый выбор: canonical → маршрут),
metrics (per-model/per-route: TTFT p50/p95, успешность, стоимость).

Control plane хранит всё остальное в SQLite (control.db): конфигурацию с
ревизиями (draft → validate → simulate → apply → rollback), провайдеров,
canonical-маппинги, пул моделей, политики, пробы доступности, историю цен,
baselines, audit log, расписание автообновления.

## 3. Первый запуск

Продукт уже развёрнут. Для новой установки: docs/install-same-host.md,
scripts/migrate-r8.sh --check, затем --execute --confirm-production.
Проверка: hermes verify --json (рецепт Model Router R8.1B).

## 4. Обзор (Dashboard)

Каждая карточка грузится независимо: ошибка одного endpoint не обнуляет
остальные. Состояния: число (значение), «Ошибка получения данных» (endpoint
+ HTTP-код), реальный 0 (пусто). Ключевые карточки: провайдеры, модели в пуле,
доступны сейчас, маршруты Router, расходы (с момента запуска, кумулятивно —
телеметрия не хранит дневные срезы), каталог (Provider A/Provider B),
несопоставленные, предложения рынка (сумма по моделям; продавцы могут
повторяться — подписано честно).

## 5. Провайдеры

Два маркетплейса: Provider A (provider-a.example) и Provider B
(provider-b.example, биржа токенов со скидкой). Секреты — только ENV
(~/.config/model-router/router.env, 0600); в UI и экспортах — только имена
переменных. Кнопка «Проверить подключение» — бесплатная проверка API/auth.

## 6. Discovery

Кнопка «Обновить данные» выполняет полный цикл: каталоги + цены рынка +
снапшоты истории цен. R13-гварды: (а) shrink-guard — сокращение каталога
провайдера более чем на 50% блокирует деструктивное обновление и создаёт
аномалию (каталог не «схлопывается» молча); (б) price sanity — отрицательные,
NaN/inf значения отбрасываются, $0 только при доказанном FREE, скачки единиц
(µUSD-конверсия Provider B) и скидки >99.99% — предупреждения.

Отдельные кнопки: «Обновить каталог» (runtime registry), «Обновить цены
рынка», «Проверить доступность» (только пул).

## 7. Каталог моделей

R12-инвентарь: 578 записей (Provider A 174 + Provider B 404), без скрытой фильтрации.
Несопоставленные провайдерные модели видны и доступны для сопоставления.

## 8. Мой пул

Модели, которые Router выбирает автоматически. Управление: членство
(убрать/вернуть), скрытие, отключение, per-model политики. «Подходит
политике» = скидка ≥ минимума + модель в пуле + не скрыта.

## 9. Несопоставленные модели

«Новые и несопоставленные» (537): провайдерные модели без canonical-маппинга.
Поиск, группировка по семействам (Claude, GPT, Gemini, ...), действия:
Сопоставить / Добавить как новую / Игнорировать. Автосопоставление — только
безопасное, с предпросмотром.

## 10. Добавление модели

Wizard: поиск по всем каталогам → выбор варианта провайдера → название +
canonical ID (предлагается автоматически) + минимальная скидка (наследование
или своя) → проверка → сохранение. Модель сразу попадает в пул со статусом
«На наблюдении».

## 11. Удаление / скрытие / отключение

Никакой одной кнопки «Удалить». Обратимые действия с подтверждением:
убрать из автоматического выбора (в каталоге провайдера остаётся),
скрыть из списка, полностью отключить (запрещена даже для fallback),
удалить сопоставление (только ручные маппинги).

## 12. Canonical mappings

Canonical — единое имя модели Router (например gpt-5.6-luna); маршруты
провайдеров маппятся на него (например cb/gpt-5.6-luna, sp:gpt-5.6-luna —
разные продавцы одной модели). Маппинги хранятся в control.db, каждое
изменение — в audit.

## 13. Рынок и предложения

Provider B: реальные продавцы (num_sellers) по каждой модели. Provider A: списки
asks — это ЦЕНОВЫЕ ПРЕДЛОЖЕНИЯ, идентичность продавца неизвестна; input/output
asks не суммируются как независимые источники. В UI: «17 предложений» (Provider A)
или «4 продавца» (Provider B); если точное число недоступно — «есть предложения».

## 14. Official / market / actual pricing

- Официальная цена — прайс провайдера без скидки (USD / 1M токенов).
- Рыночная цена — лучшее текущее предложение (для Provider B — с учётом скидки
  продавца; конверсия µUSD→USD проверена, 39/39 моделей совпали с live-данными).
- Фактическая — из биллинга (Provider B x-si-buyer-cost-micro). Бейджи
  «Оценка»/«Фактически» никогда не смешиваются.

## 15. Price freshness

Возраст каждого снапшота: «37 секунд назад», при старше 2 часов — бейдж
«Цена устарела». Баннер «Данные рынка обновлены: 23:17:42» + состояние каждого
провайдера (свежие/устарели/нет данных) + расписание автообновления
(следующее обновление через N мин, последняя ошибка если была).

## 16. Price history

Снапшот цен при каждом обновлении. Окна: сейчас / 1 час / 24 часа / 7 дней /
30 дней (min/avg/max по цене и скидке). Для несопоставленных моделей — история
по маршруту провайдера. Накапливается с R12; полный цикл автообновления — R13.

## 17. Контекст

Контекст указывается по каждому маршруту (фейковые 1M-фоллбеки удалены в R11).
Если провайдер не отдаёт — «неизвестен», никогда не выдумывается.

## 18. Availability checks

Пробы через backend (UI никогда не ходит к провайдерам напрямую).
Бесплатные: доступность API, auth, наличие модели в каталоге. Платные
(inference-проба, max_tokens=16) — только по явному действию. Bulk-кнопка
«Проверить доступность» проверяет ТОЛЬКО модели пула, с прогрессом.

## 19. Latency / TTFT

Из реальных проб и трафика: TTFT p50/p95, total p50/p95, success rate,
samples. При малой выборке — «Недостаточно данных». В основной таблице:
«Быстро: 1.2 с TTFT» / «Медленно: 8.4 с TTFT», детали — в drawer.

## 20. Per-model minimum discount

Модель → Политика: «Использовать общий минимум: 80%» или «Свой минимум: 90%».
Живой предпросмотр: рынок сейчас vs ваш минимум (✓ подходит / ✗ не
используется). «Вернуть общее значение» — сброс наследования. Реализовано
через bid-заголовки (Provider A x-max-*-price, Provider B X-Min-Discount).

## 21. Global routing policy

Вкладка «Маршрутизация»: пороги выбора, экономика, cache affinity. Изменения —
только через ревизии (draft → validate → simulate → apply). Жёсткие гейты
(health, качество, контекст) всегда до экономики.

## 22. Почему Router выбрал модель

Кнопка «Почему?» в каждой строке: чек-лист с ✓/✗ (сопоставлена, N маршрутов,
скидка ≥ минимума, контекст, health), лучший маршрут и его цена. Для
непрошедших — причина отклонения и вердикт «не участвует в авто-выборе».

## 23. Cost calculator

«Калькулятор стоимости»: модель, input/output/cache-read токены, пресеты
(10k+2k ... 1M+20k). Результат: лучший рынок сейчас / максимум по вашей
политике / официальная / экономия в $ и %. Сравнение по провайдерам.
Форматирование: $0.0040, а не $0.00 (4–6 знаков для дешёвых цен).

## 24. Provider A specifics

Asks = ценовые предложения без идентичности продавца. min_ask_in/out — USD
за 1M. Скидка считается vs official. Двойной подсчёт in/out asks исключён.

## 25. Provider B specifics

Рынок = реальные продавцы. Цены /api/markets приходят в µUSD за 1M —
конвертируются ÷1e6 (проверено живыми данными). 404 minimum_discount_not_met
на /min80/ — реальное состояние рынка, не ошибка. Фактическая оплата —
заголовок x-si-buyer-cost-micro.

## 26. Overrides

Временные переопределения маршрутизации (force canonical/route, prefer
provider, disable) с TTL. Персистентные — через политики, не overrides.

## 27. Simulator

Вкладка «Симулятор»: выбор задачи → предпросмотр, какая модель/маршрут будет
выбраны и почему, без реального запроса.

## 28. Audit / Revisions

Человеческий формат: дата, действие («Изменена политика модели... Минимальная
скидка: 80% → 90%»), автор, статус. Raw JSON — под «Для разработчика»
(диагностический режим). Ревизии конфигурации: полный цикл с diff и impact.

## 29. Known-good baseline

«Настройки» → «Создать точку восстановления». Immutable-снапшот: провайдеры,
маппинги, пул, политики, глобальная политика, алиасы, таймауты. НЕ входят:
секреты, метрики, биллинг, снапшоты цен. Baseline: id, SHA-256, schema_version,
created_at, description, исходный коммит.

Активный: base-knowngood-5748bc15, SHA-256 2e9d51a99fe57451..., «KNOWN-GOOD
2026-09-11 (R12-B, ff75cef)».

## 30. Restore / rollback

«Восстановить baseline» → предпросмотр diff → подтверждение → применение
через ревизии и audited-сеттеры (никаких прямых записей в БД). Полный откат
продукта: docs/rollback.md (legacy hermes-router.service).

## 31. Backup

- control.db: автоматические копии при миграциях + control.db.bak-*
- Конфиг: docs/reference/current-known-good-config.json (без секретов),
  import dry-run PASS.
- Секреты: только ~/.config/model-router/router.env (0600) — в бэкапах
  product-tree отсутствуют.

## 32. Типовые неисправности

- «Цена устарела» везде → нажать «Обновить данные»; если остаётся — ошибка
  провайдера в баннере свежести.
- Карточка «Ошибка получения данных» → конкретный endpoint недоступен;
  посмотреть journalctl --user -u model-router-control.service -e.
- Пустой стрим у клиента → известный хвост двойного [DONE] (provider raw +
  router); клиенты останавливаются на первом.
- Аномалия «каталог сократился» → shrink-guard заблокировал обновление:
  проверить провайдера вручную, затем «Обновить данные» ещё раз.

## 33. Диагностика

SIGUSR1 в control-процесс — дамп всех стеков в journald. Failover-trace:
state/<instance>/failover-trace.jsonl (без промптов/ключей). Диагностический
режим UI (Настройки → Диагностика): canonical ID, provider model ID, raw JSON.

## 34. Команды

    systemctl --user {start|stop|restart|status} model-router.service
    systemctl --user {start|stop|restart|status} model-router-control.service
    curl -s localhost:4100/health        # runtime
    curl -s localhost:4111/healthz       # control
    journalctl --user -u model-router-control.service -e
    cd ~/model-router && .venv/bin/python -m pytest gateway_tests -q
    hermes verify --json                 # рецепт Model Router (R8.1B)
    /tmp/mr-e2e-venv/bin/python state/e2e/e2e_r12b.py   # browser E2E

## 35. Recovery

1. Быстрое восстановление конфигурации: Настройки → Восстановить baseline
   (diff → подтверждение).
2. Импорт JSON: docs/reference/current-known-good-config.json → Импорт
   (валидация → подтверждение → применение).
3. Восстановление control.db: остановить control, подложить бэкап
   control.db.bak-*, запустить.
4. Полный откат на legacy: docs/rollback.md.

## Приложение А. Словарь простым языком

- DISCOVERED (обнаружена) — модель есть в каталоге провайдера.
- IN POOL (в моём пуле) — разрешена для автоматического выбора Router.
- AVAILABLE (доступна) — можно купить прямо сейчас (маркет активен).
- ON MARKET (на рынке) — есть активные предложения продавцов.
- ELIGIBLE (подходит политике) — доступна И в пуле И скидка ≥ минимума.
- MATCHED (сопоставлена) — провайдерная модель связана с canonical-моделью
  Router. UNMATCHED — не связана; Router её не видит до сопоставления.

## Приложение Б. Маршрут vs предложение vs продавец

- Провайдер — маркетплейс (Provider A, Provider B).
- Provider model ID — имя модели у провайдера (cb/gpt-5.6-luna).
- Canonical model — единое имя модели в Router (gpt-5.6-luna); несколько
  provider model ID могут маппиться на один canonical.
- Маршрут (route) — конкретный путь исполнения: провайдер + модель.
  «Маршруты Router: 34» = 34 таких пути в runtime.
- Предложение (offer/ask) — ценовое предложение на рынке. У Provider A это
  ценовые заявки без известных продавцов; сумма 524 — по всем моделям.
- Продавец (seller) — реальный продавец Provider B; сумма 211 по моделям,
  продавцы могут повторяться между моделями (подписано в UI).
